# Translation

Pretty Please Print speaks English, and French on the screens that have been
translated so far: **the sign-in page and the header** (its navigation, the
Activity panel, the account menu and the passkey nudge), the preferences on
`/me`, the defaults on `/admin/settings`, a ticket's slicer button and the
first-run setup at `/admin/setup`, which is translated as a whole.
Everything else is still English. The rest follows a screen at a time, as asked in #103 — small
steps, each one reviewable.

## How it works

- **[next-intl](https://next-intl.dev), with no locale in the URL.** There are
  no `/fr/…` routes and no next-intl middleware. Every link, every redirect and
  every `next=` parameter is exactly what it was, and so is every bookmark.
- **The language is chosen per request**, by one function:
  `resolveLocale` in [src/i18n/locales.ts](../src/i18n/locales.ts), in this
  order:
  1. the person's own choice — `User.preferredLocale`, set on `/me`;
  2. the browser's `Accept-Language` — matched on the primary subtag (`fr-CA`
     gets French), by `q=` weight, a malformed header counting as none;
  3. the instance's default — *Language* under "For everyone who has not
     chosen" at `/admin/settings`;
  4. English.

  A choice made in the app beats the browser; the instance's default comes
  after the browser, because it is a guess about a stranger and the browser is
  better placed to make it. A signed-out page starts at 2. With nothing set,
  this is exactly what happened before translation existed. The comment on
  `LocaleSources` gives the reasoning.
- **`messages/en.json` is the source of truth.** Every key is a type
  ([src/i18n/app-config.d.ts](../src/i18n/app-config.d.ts)), so asking for a key
  English does not have — a typo, or one removed while a component still uses
  it — fails `npm run typecheck`.
- **A translation is laid over English, key by key**
  ([src/i18n/request.ts](../src/i18n/request.ts)). A key French has not caught up
  with shows in English, never as its own name; so does an empty string, or a
  value of the wrong shape.
- **`<html lang>` follows the language**, and so does `relativeTime` on the
  translated screens (`getRelativeTime` in
  [src/i18n/server.ts](../src/i18n/server.ts)). Screens that are not translated
  keep English times, so a page never reads "il y a 3 heures" in the middle of
  an English sentence.

### Why next-intl, and what it costs

It is the App Router's de-facto library: server components, server actions and
client components all read the same catalogue, ICU plurals come with it, and it
works without locale routing — which is the one thing this app needed it not to
impose. Writing the equivalent here would mean owning a message formatter.

- **Licence:** MIT. What it pulls in is MIT, Apache-2.0 (`@swc/*`) and
  BSD-3-Clause (`intl-messageformat`) — all compatible with AGPL-3.0.
- **Pinned exactly at 4.14.9**, the newest release when it was added. Not an
  older, leaner 4.x: everything before 4.9.2 carries a published advisory
  (an open redirect in its middleware, and prototype pollution through an
  experimental precompile option). Neither is reachable here — this app runs
  neither — but both would be reported by every scan for as long as the pin
  stood.
- **The weight is build-time.** Since 4.5, next-intl depends on `@swc/core` and
  `@parcel/watcher` for a message extractor this app does not use; with their
  platform binaries that is most of the ~50 lockfile entries it adds, and both
  run an install script during `npm ci`. None of it reaches the runtime image:
  the standalone bundle the runner copies traces no `@swc/core`, no
  `@parcel/watcher` and no `@eloqnt/*`, and next-intl itself is compiled into
  the server chunks.
- **One lockfile entry npm 11 drops and npm 10 needs.** `@swc/core` asks for
  `@swc/helpers >=0.5.17` as an *optional* peer, and Next pins `0.5.15` at the
  root. npm 10 — the one in `node:22`, so the one CI and the Dockerfile run
  `npm ci` with — nests `0.5.23` under next-intl and refuses a lockfile without
  it ("Missing: @swc/helpers@0.5.23 from lock file"). npm 11 leaves the peer
  unresolved and, on any `npm install`, deletes the entry. The committed
  lockfile has it, and `npm ci` passes under both. If a later install removes
  it, CI's first step fails with that message: put
  `node_modules/next-intl/node_modules/@swc/helpers` back, or run the install
  with npm 10.

### What stays English, on purpose

The JSON API, the OpenAPI document and the console at `/docs`; audit verbs
(`story.created`, …) and every log line; e-mails; the PrusaSlicer helper.
These are read by programs, by the operator, or by whoever debugs a problem —
and one language there is what makes an error message searchable.

Two things are English *for now*, and are known gaps rather than decisions:

- **Notification text.** It is written into the database as an English sentence
  when the notification is created, so the Activity panel lists English items
  under a French title. Translating it means storing a key and its values
  instead of a sentence.
- **Messages from Better Auth** (a refused passkey, for one). They come from the
  library, not from a catalogue this app owns.

### `lang="fr"` over English pages

While only two screens are translated, a French reader opening `/board` gets a
French header over English content, all under `<html lang="fr">` — so a screen
reader reads the English in a French voice. The alternative, keeping
`lang="en"` until every screen is done, would read the translated header wrong
instead, and would make "follows the language" a promise kept only at the end.
Translating screen by screen shrinks the problem with each step; if it proves
worse than that in practice, the untranslated pages can mark their own content
`lang="en"`.

### The choosers on `/me` and `/admin/settings`

Both are new, so both are translated — over pages that are not yet, the same
way the header is. A French reader of `/me` gets English statistics above a
French *À votre goût*, and a French owner the same at `/admin/settings`; each
page goes French as a whole when its turn comes. Languages are listed in their
own words (`LOCALE_NAMES`: *English*, *Français*) whatever the page's
language, because that is the word someone looking for their language looks
for. The same goes for the slicer button on a ticket, whose label, sending
link and help line are in the `slicer` group.

## Adding a key

1. Add it to `messages/en.json`, under the group for its screen
   (`signin.form.…`, `header.nav.…`). Name it for what it *is*, not for its
   English words — `header.nav.books`, not `header.nav.theBooks`.
2. Use it: `const t = await getTranslations("signin")` in a server component,
   `const t = useTranslations("signin.form")` in a client one, then `t("key")`.
   Arguments are ICU: `"{count, plural, one {# passkey} other {# passkeys}}"`
   with `t("passkeys", { count })`.
3. Add the French to `messages/fr.json`, at the same path. **If you do not
   write French, leave it out.** The French page shows your English text for
   that key, `npm run check:messages` lists it as a warning, and CI passes with
   a warning annotation on the pull request — which is how the translator hears
   about it. Do not paste the English into fr.json to silence the warning: that
   hides the key from the one check that would have found it.
4. `npm run typecheck && npm run check:messages`.

When you **change the meaning** of an English string, change or remove its
French too: the check sees keys, not meanings, and a French sentence that says
what the English used to say will pass it. When you **rename a placeholder**,
the French key fails the check until it follows (see below) — rename it in
fr.json too, or delete the French key and let it show in English.

## What `check:messages` reports

[scripts/check-messages.ts](../scripts/check-messages.ts) holds every file in
`messages/` against `en.json`. It runs in CI's `guard` job and in
`scripts/full-test.sh`.

**Warnings** are listed and the check still passes. Each is what an
English-only change leaves behind, and each costs a French reader nothing but
some English — the page falls back key by key. A maintainer who does not write
French must be able to merge; the translation catches up after. Under GitHub
Actions each warning is also a `::warning` annotation, so it shows on the pull
request, and `full-test.sh` adds a `WARN check-messages` line to its summary.

| warning | means | do |
|---|---|---|
| **missing** | in English, not in the translation | translate it (it shows in English until then) |
| **stale** | in the translation, gone from English | delete it |
| **shape** | a string against a group, or the reverse | match English's new structure |

Stale is a warning rather than an error for the same reason as missing:
removing or renaming an English key is an English-only change, and the French
left behind is never read by anything.

**Errors** fail the check. These are broken, not merely behind:

| error | means | do |
|---|---|---|
| **empty** | `""` | translate it, or remove the key |
| **arguments** | `{name}`, `{count}`… differ from English | keep every placeholder, renamed nowhere |
| **quote** | an ASCII `'` right before `{`, `}` or `#` | use the typographic `’` |
| **malformed** | not JSON, a key containing `.`, a value neither string nor group | fix the file |
| **client components** | a `useTranslations("x")` in a `"use client"` file whose group the browser is not sent | add the group to `CLIENT_GROUPS` |

**quote** is ICU's quoting rule: an ASCII apostrophe before a brace starts a
quoted literal, so `l'{x}` renders as "l{x}" with no error anywhere. The
catalogues use `’` throughout, which ICU leaves alone.

## Translating a screen

- Server component: `getTranslations("group")`. Client component:
  `useTranslations("group")` — and add the group to `CLIENT_GROUPS` in
  [src/i18n/client-groups.ts](../src/i18n/client-groups.ts). Only those groups
  reach the browser: the whole catalogue would put the admin's navigation into
  a client's page source, where `verify:auth` asserts it is absent. A group
  left off the list would render as key names; `check:messages` fails first.
- A time: `const ago = await getRelativeTime()`, then `ago(date)`.
- A screen inside `AuthShell` passes its banner as `sign={…}`; the shell stays
  English for the screens that do not.
- **English must not change by a byte.** Every suite reads English copy. Add a
  check that the screen renders French for `Accept-Language: fr` and the same
  English as before without it — `verify:auth`'s section 15 is the pattern.
- Browser-driven scripts send `Accept-Language` explicitly (English in
  `verify:passkey`; `SHOT_LANG`, default English, in `npm run shots`), because
  Chrome otherwise asks for the machine's locale.

## Adding a language

1. Add its code to `LOCALES` in [src/i18n/locales.ts](../src/i18n/locales.ts).
2. Add `messages/<code>.json` and a loader for it in `CATALOGUES` in
   [src/i18n/request.ts](../src/i18n/request.ts) — the typecheck insists on the
   second once the first is done.
3. `npm run check:messages` picks the file up by itself and lists everything
   still to translate, as warnings: a half-translated language can ship, and
   shows English wherever it has not caught up.
4. Add a glossary section here: the diner words are where a translation goes
   wrong, and the reasoning is what the next translator needs.

## French

### Conventions

- **Vous**, throughout. A waiter says *vous* to a customer. A family instance
  might prefer *tu*; that would be a change to the whole catalogue at once, not
  key by key.
- **Typography:** the apostrophe is `’`; a narrow no-break space (` ` in
  the JSON) goes before `?`, `!` and `;`; guillemets are `« … »` with no-break
  spaces inside.
- **Passkey** is *clé d’accès*, the term Apple, Google and Microsoft all use in
  French — it is what people will see in their own system's prompt.
- Gender: *invité* stays the grammatical masculine generic in running text; the
  person who owns the printer is *la personne qui s’occupe de l’imprimante*,
  which needs no agreement at all.

### The diner, in French

The voice is part of the product: a 1950s diner, the owner in the kitchen, the
members at the counter. The aim is a French *bistrot* or *routier* kitchen, not
a dictionary — the word a French cook would say, where one exists.

| English | French | Why |
|---|---|---|
| The rail | **Le rail** | Order tickets hang on a rail in French kitchens too (*le rail*, *la barre à bons*). *Les bons* is the cooks' word for the tickets themselves, but on a menu chip it reads as "the good ones" to anyone outside a kitchen. |
| The pass | **Le passe** | The counter between kitchen and room where a plate is checked before it goes out. Same word, masculine, in every French kitchen — and the owner's queue is exactly that. |
| Order up | **Passer commande** | "Order up!" is the cook's call. Its French counterpart, *Ça marche !*, answers an order rather than placing one, and as a link reads as "it works". *Passer commande* is what you do at a counter. |
| My orders | **Mes commandes** | |
| The books | **La caisse** | The owner's page of everything that went through, under the kicker "Behind the counter". The till is the counter's word for that; *les comptes* would collide with people's accounts. |
| Members only · ask at the counter | **Réservé aux habitués · demandez au comptoir** | *Les habitués* — the regulars — are who a bistrot lets in without asking. |
| What’ll it be? | **Qu’est-ce que je vous sers ?** | What a French waiter actually says. |
| Open · come on in | **Ouvert · entrez donc** | The sign on the door, and the invitation with it. |
| whoever owns the printer | **la personne qui s’occupe de l’imprimante** | Neutral, and in a family instance *le propriétaire* sounds like a landlord. |
| Printer owner / Invited member (role) | **Propriétaire de l’imprimante** / **Membre invité** | A label, so kept plain. |
| New from the group | **Du nouveau en salle** | The owner is in the kitchen; the members are *en salle*, in the dining room. |
| Updates on your prints | **Où en sont vos impressions** | |
| Feature requests | **Boîte à idées** | The suggestion box every French café and office has. |
| Benefits | **Pourboires** | The list is the tip catalogue; *pourboire* is the word. |
| Guest list | **Liste des invités** | |
| Materials | **Matières** | A filament is a *matière*, and the word is also a kitchen's raw ingredients. |
| Audit | **Journal** | What French software calls a log someone reads. |
| nothing to phish | **rien à se faire voler** | *Hameçonner* is correct and reads as jargon to the people this is for. |
| just now | **à l’instant** | `Intl` has no "just now"; this is the phrase. |
| slicer | **trancheur** | The word the French 3D-printing community and the slicers' own French translations use; *slicer* reads as English jargon. Slicer names (PrusaSlicer, OrcaSlicer…) stay as they are: they are names. |
| How you like it | **À votre goût** | The preferences on `/me`: how a diner asks how you take it. |
| Same as the house | **Comme la maison** | A choice left to the instance — *la maison*, the house, as in *la spécialité de la maison*. |
| Diner / Diner after hours | **Le diner, de jour** / **Le diner, de nuit** | The two themes. *Diner* alone would read as *dîner*, a meal; the day and the night say which. |
| First-run setup · Before the doors open | **La mise en place** | What a French kitchen calls everything done before the first service — exactly what the setup is. Its kicker, *Premier service*, is the service it prepares for. |
| the helper (slicer) | **l’assistant** | The small program installed once per machine. *Gestionnaire* would read as a file manager. |
